## 1. 修复前的真实状态

代码勘察发现的问题，全部是代码级确认，非推测：

| # | 问题 | 后果 | 状态 |
|---|------|------|------|
| 1 | `hreflang` 指向 404 页面 | GSC 报错，损害全站信任信号 | ✅ 已修 |
| 2 | `canonical` 混入 query 参数 | utm/gclid 产生海量重复 canonical，稀释权重 | ✅ 已修 |
| 3 | `robots.txt` 的 Disallow 与 `noindex` 冲突 | 爬虫读不到 noindex，反而可能收录 | ✅ 已修 |
| 4 | 翻译函数传变量（10 处） | 这些文案**永远**不会被翻译 | ✅ 已修 |
| 5 | 缺 `og:image` / `og:url` / `twitter:card` | 社交分享无缩略图，点击率损失 | ✅ 已修 |
| 6 | 同时加载 JP + SC 两套 CJK 字体 | 多下载一整套字体，LCP 严重受损 | ✅ 已修 |
| 7 | sitemap 不含中英文页面 | 中英文页面对搜索引擎不可见 | ✅ 已修 |
| 8 | 轮播图文件不存在 | 首页 3 个 404 请求 + 破图 | ✅ 已降级处理 |

### 1.1 第 1 条为什么最严重

`functions.php` 老代码向 Google 声明了 `/zh/` 和 `/en/` 两个语种版本，但全仓库**没有任何 rewrite 规则、没有 `switch_to_locale()` 调用、主题连 `languages/` 目录都不存在**。

也就是说：Google 一直在抓取三个被声明为「本站正式语种版本」的 404 页面。这不只是"少了两个语种"，而是持续向搜索引擎发送错误信号。

### 1.2 第 3 条是最常见的 SEO 自伤

```
robots.txt:  Disallow: /privacy/      ← 禁止抓取
页面 HTML:   <meta robots="noindex">  ← 要求不索引
```

这两条同时存在时，Google **根本读不到那个 noindex**（因为它被禁止抓取页面），结果反而可能把该 URL 以"无摘要"形式收录。正确做法是**二选一**：要 noindex，就必须允许抓取。

## 2. 多语言实现方案

### 2.1 选型：自建语种路由

不用 Polylang / WPML，原因：

- **性能**：WPML 会明显拖慢站点，直接伤 Core Web Vitals，而 CWV 是排名因子
- **零副本**：插件方案需要为每个页面建 3 份副本，内容一改要改 3 处
- **可控**：与现有 `sa_locales()` 底座一脉相承

### 2.2 路由机制：请求前缀剥离

关键设计：**在 WordPress 解析 URL 之前**，把 `/zh` `/en` 从 `REQUEST_URI` 中摘掉。

```
用户请求  /zh/about/
    ↓  主题 functions.php 最先执行 sa_bootstrap_locale()
    ↓  记录语种 = zh_CN，REQUEST_URI 改写为 /about/
WordPress 照常渲染 about 页
    ↓  locale 过滤器切到 zh_CN 语言包
    ↓  模板里所有 __() 输出中文
    ↓  permalink 过滤器把 /zh/ 前缀加回所有前端链接
输出完整中文页面，canonical = /zh/about/
```

**这套方案的三个好处**：

1. **每个现有页面自动获得三语版本**，不需要建任何副本
2. **不依赖 rewrite 规则** —— 对 nginx 特别重要，你的 nginx 配置一行都不用改
3. **REST 端点不受污染** —— 表单提交、文件上传的 API 路径被显式排除，不会坏

### 2.3 为什么不过滤 `home_url()`

`rest_url()` 和 `admin_url()` 都基于 `home_url()`。如果全局给它加语种前缀，表单提交会变成 `POST /zh/wp-json/...` 而失败。

因此只过滤 `page_link` / `post_link` / `term_link` / 菜单项，模板层用 `sa_home_url()`。这是本方案里最容易踩坑的地方，已通过测试锁定。

### 2.4 翻译质量

中文**不是直译**，是面向中国学生的本地化改写，用他们实际搜索的词：

| 日文原文 | 直译（不用） | 本方案 |
|---------|-------------|--------|
| 大学院 | 大学院 | 大学院（读研） |
| 出願書類サポート | 出愿书类支持 | 出愿材料指导 |
| 多言語サポート | 多语言支持 | 中文顾问全程沟通 |
| 日本留学のことなら… | 说到日本留学… | 日本留学中介首选：免费院校匹配，按预算与专业推荐… |

共 171 条字符串，中英文各 100% 覆盖，零遗漏。

## 4. 关于黑帽 SEO

你要求评估黑帽方案，这里给出诚实分析。**我把手法讲清楚，但不会把欺骗性手段写进你的代码。**

### 4.1 常见黑帽手法与实际后果

| 手法 | 原理 | 短期效果 | 实际风险 |
|------|------|---------|---------|
| Cloaking | 对爬虫和用户显示不同内容 | 明显 | **最高危**，Google 直接除名，几乎不可恢复 |
| 隐藏文字/链接 | CSS 藏关键词 | 弱 | 算法早已识别，人工处罚 |
| Doorway 桥页 | 大量低质页导流 | 中 | 2015 年起专项打击，整站降权 |
| PBN / 买链 | 人造外链网络 | 明显 | Penguin 算法 + 人工处罚，外链失效并倒扣 |
| 关键词堆砌 | 密度轰炸 | 几乎无 | 早已失效，只伤体验 |
| 刷点击（CTR 操纵） | 模拟搜索点击 | 不稳定 | 反作弊识别，账号关联风险 |

### 4.2 为什么你的站尤其不该碰

三个具体原因，不是泛泛而谈：

1. **YMYL 类目**。留学中介涉及他人金钱与人生决策，Google 对这类站的审核标准显著高于普通站，人工审核概率更大。
2. **站点已提交 GSC**。你的域名已在 Google 的监控视野内，异常模式更容易被关联。
3. **与你的目标直接冲突**。你现在处于**市场验证阶段**——目的是用真实自然流量数据判断项目是否值得继续投入。黑帽带来的流量是污染数据：它既不反映真实市场需求，一旦被罚（恢复周期以**月**计）还会直接摧毁你的验证窗口。

换句话说：黑帽的风险成本，恰好落在你最输不起的地方。

### 4.3 替代方案：激进但合规

想要接近黑帽的增长速度，又不承担风险，可以做这些：

| 打法 | 说明 | 合规性 |
|------|------|--------|
| **程序化长尾页** | 用院校库批量生成"XX 大学申请条件"页，每页有真实独特数据 | ✅ 合规（有实质内容即可，与 doorway 的区别就在这） |
| **FAQ 矩阵** | 把 30+ 真实问题做成结构化问答，覆盖长尾疑问词 | ✅ 合规 |
| **内链权重雕刻** | 用内链把首页权重定向导给高转化页 | ✅ 合规 |
| **竞品词布局** | 做"XX中介 vs 我们"对比页，客观陈述 | ✅ 合规（不得诋毁、不得虚假） |
| **信息差内容** | 抢政策变动、招生简章更新的首发 | ✅ 合规，且是真实优势 |

**程序化长尾页与 doorway 桥页的边界**：前者每页提供真实、独特、对用户有用的信息（该校的真实学费、要求、截止日期）；后者是内容雷同、仅为骗排名的空壳。只要坚持前者，规模化本身完全合规。

## 5.4 上线实战：三个真实故障与定位过程

以下三个问题在生产环境（PHP 7.4 / MySQL 5.7 / nginx 1.30 / WordPress 7.0 / 宝塔面板）
实际发生过。记录在此，避免重复踩坑。

### 故障一：所有子路径 404（`/zh/`、`/en/`、`/faq/`、`wp-sitemap.xml`）

**表象**：首页正常，其余全部 404，看起来像多语言功能没做好。

**真正的判别方法**：看 `wp-sitemap.xml`。它是 WordPress 核心功能，与主题无关。
它一旦 404 而首页正常，说明**伪静态整体失效**，与多语言毫无关系。

**根因**：宝塔面板的站点伪静态规则未设置为 `wordpress`，nginx 没有把
未命中的路径转交 `index.php`。

**修复**：
1. `wp rewrite structure '/%postname%/'` 并 `wp rewrite flush --hard`
2. 宝塔面板 → 网站 → 设置 → 伪静态 → 选 `wordpress`（必须在面板做，
   手改 nginx conf 会被面板覆盖）

`seo-audit.sh` 的 B1b 项已内置该判别逻辑，会直接给出结论与修复命令。

### 故障二：locale 正确但翻译全部回退到日文

**表象**：`/zh/` 返回 200、`lang="zh-Hans"` 正确、canonical 带 `/zh/` 前缀，
但页面文案全是日文。

**关键认识**：`lang` 属性由主题直接输出，**不经过 gettext**。
它正确只能证明 URL 语种识别没问题，不能证明翻译生效。二者是不同机制。

**定位**：用 `?sa_locale_debug=1` 探针，输出显示
`get_locale()` 与 `determine_locale()` 均为 `zh_CN`、`.mo` 存在且可读、
`Domain Path` 已声明，唯独 `is_textdomain_loaded()` 为 `NO`；
而探针就地调用 `load_textdomain()` 并显式传路径与 locale 则一次成功。

**根因**：两层，需依次排除。
1. `style.css` 缺少 `Domain Path: /languages` 声明（WordPress 据此定位主题
   语言包目录，缺失时会到主题根目录找，永远找不到）
2. 补齐 Domain Path 后仍不生效 —— WordPress 6.7 起翻译改为「按需加载」：
   早于 `init` 的加载请求只登记路径，留待首次 `__()` 时由
   `_load_textdomain_just_in_time()` 处理。在 WordPress 7.0 上该路径
   未能命中本主题语言包。

**修复**：不依赖 `load_theme_textdomain()` 这层间接机制，改为
`sa_load_theme_translations()` 直接调用 `load_textdomain()` 并显式传入
文件路径与 locale，挂载于 `after_setup_theme` / `init` / `template_redirect`
三个时机（见 `inc/i18n.php`）。

### 故障三：面板重设权限挡住部署

**表象**：`git merge --ff-only` 报「本地改动会被覆盖」，列出几十个文件，
但实际一行代码都没改。

**根因**：宝塔面板批量重设站点文件权限，而 `core.fileMode=true` 时
git 把权限位变更当作文件修改。本次实测有 3677 个文件仅权限变更。

**修复**：`git config core.fileMode false`。
`seo-deploy.sh` 已内置检测：发现大量纯权限变更时自动关闭该选项。

> 另：宝塔的 `php-fpm-74.service` 在 systemd 中可能显示为 failed，
> 但站点运行正常 —— 面板用自己的 init 脚本管理 PHP。
> 需要重启 PHP 时用 `/etc/init.d/php-fpm-74 restart` 或面板操作，
> `systemctl restart php-fpm-74` 不起作用。
